## 1. 背景与目标

管理对象是服务器设备**内部的核心配件**,而非服务器整机。配件会频繁发生迁移、增配、调配、减配、借出等流动。当数量与种类一多,极易出现找不见、无法溯源的情况,进而造成国有资产流失。

纳管的七类核心配件:**内存、机械硬盘、固态硬盘、HBA 卡、网卡、光模块、GPU 卡**。

配件来源有两类:随器采购(跟服务器一起买)与单独合同采购;另有维保换新产生的新件。

**核心目标:**
- 每一件配件可**逐件溯源**(带唯一固定资产编号,从入库到当前的全程可追)。
- 账实一致:系统记录与实物状态始终对得上。
- 对高风险流动(借出到外单位、调拨、报废)设审批闸门,防流失。

## 3. 核心设计原则

1. **三层数据结构**:型号库(规格)/ 配件实物(逐件)/ 履历(流水),职责分离。
2. **履历只增不改不删(append-only)**:任何变动都是插入新记录,永不 UPDATE / DELETE 历史。这是溯源的命根。
3. **当前状态是投影,不是真相**:配件"当前在哪、什么状态"由履历最新一条投影得出;实物表可缓存一份加速查询,但真相只在履历里。
4. **同一事实不存两遍**:配件的"投运状态"不单独存储,由所在服务器的运行状态**派生**(见 5.3),杜绝级联刷值导致的账实不符。
5. **边界定审批**:配件停留在本单位数据中心内→仅需运维快速留痕(备案);一旦跨出本单位边界(借出/调拨到外单位)→走审批。
6. **报废是边界规则的唯一例外**:报废一律审批,不看配件在不在本单位(国有资产处置有规定)。
7. **不过度设计**:兼容性硬校验、审批"打回修改"等一期不做,留字段、给软提示,由真实使用驱动后续增强。

## 4. 数据模型

### 4.1 `part_model` 型号库(规格住这里,维护一次)

| 列名 | 类型 | 说明 |
|---|---|---|
| work_order_no | 字符串 | 关联工单号,接入现有工单系统;让每次流动挂在具体工单上(本系统相对通用产品的核心优势) |

**事件类型(7 种原子事件),及备案/审批归属:**

| event_type | 备案 / 审批 | 触发条件 / 说明 |
|---|---|---|
| 入库 | 备案 | 新件/退还件/换新件进库 |
| 装机 | 备案 | 库位 → 服务器 |
| 拆下 | 备案 | 服务器 → 库位。**前提:该服务器 run_status ≠ 投运**(见 5.3 锁拆) |
| 借出 | **审批** | 到外单位,会归还;须带预期归还日 |
| 归还 | 备案 | 借出件回到本单位,做收货确认 |
| 调拨 | **审批** | 永久转给外单位,所有权变更(终态) |
| 报废 | **审批** | **不看位置,一律审批** |

> 说明:**"换新"不是独立事件**。它由"旧件报废 + 新件入库"两条记录 + 同一 `event_group_id` 表达(见 6.2)。如此保证每行履历 = 某一件配件的一次原子状态跃迁。

**审批约束(硬规则,落库时校验):**
- **逐级推进**:第 N 级通过后,第 N+1 级才由"待审"激活。
- **一票否决**:任意一级驳回 → `approval.overall_status = 驳回`,流程立即结束;需重新发起新审批单。
- **回避**:`applicant_id` 不得出现在任何一级 `approver_id` 中,且三级 `approver_id` 互不相同。
- **落履历时机**:仅当 `approval.overall_status = 通过`,才向 `movement_log` 写入对应的状态变更记录,并回指 `approval_id`。被驳回/撤回的申请**不产生**任何配件状态变更,但审批单本身留痕可查。

## 5. 状态机

### 5.1 配件状态机(七态)

**状态:** 在库 / 在用 / 损坏 / 在途 / 借出 / 已调拨 / 报废

- **在库**:在本单位库房。
- **在用**:已装入某台服务器。
- **损坏**:坏件从服务器拆下、等待处置(维保换新模式,不送外修)。
- **在途**:借出/调拨/归还过程中的中转态。
- **借出**:借给外单位,会归还(带预期归还日 + 超期报警)。
- **已调拨**:永久转给外单位(终态,所有权已转移)。
- **报废**:终态。

**流转(→ 表示 event_type;【审批】/【备案】为闸门):**

- 在库 ⇄ 在用:装机 / 拆下【备案】(拆下前提:所在服务器非投运)
- 在用 → 损坏 / 在库 → 损坏:坏件拆下【备案】
- 在库 → 在途 → 借出:借出【审批】
- 借出 → 在途 → 在库:归还【备案,收货确认】
- 在库 → 在途 → 已调拨:调拨【审批】
- 在库 → 报废 / 损坏 → 报废:报废【审批】

> 借出/调拨的来源不限于"在库":若配件在未投运服务器上,允许先"拆下入库"再借出/调拨(见 5.3)。

### 5.2 服务器状态机(三态)

**状态:** 未投运 / 投运 / 退役

- 未投运 ⇄ 投运:上/下线
- 投运 / 未投运 → 退役:退役(终态)

### 5.3 两台状态机的联动规则(三条,务必实现)

1. **投运派生**:配件"是否在运行"不单独存储,实时读所在服务器的 `run_status`。即 `配件运行状态 = 所在服务器.run_status`(仅对"在用"配件有意义)。服务器投运/下线时,其上在用配件的运行状态**自动跟随**,无需写任何数据。
2. **投运中锁拆**:服务器 `run_status = 投运` 时,禁止对其上在用配件触发"拆下"事件。要动配件,先将服务器切到"未投运"。
3. **退役强制逐件处置**:服务器转"退役"**不得级联报废**其上配件(防止借服务器退役批量核销好件)。应触发一份**逐件处置清单**,列出该机所有在用配件,要求经办人对每一件明确去向(拆下入库 / 报废 / 调拨…),每件各自走对应的备案或审批。

## 6. 关键业务规则补充

### 6.1 借出超期

借出记录必须带**预期归还日期、经办人、审批人**。系统对**超期未归还**的借出主动报警。审批是借出的门槛,超期预警是追回的保险。

### 6.2 维保换新(无送外修)

服务器均带维保,损坏不修、直接换新。换新在履历中表达为**两条记录 + 同一 `event_group_id`**:

- 旧件:`event_type=报废`,`reason_code=` 返厂换新(非数据介质)/ 本单位销毁(硬盘、SSD 等数据介质,坏盘留本单位自行销毁),`status_to=报废`。
- 新件:`event_type=入库`,`part.source_type=维保换新`,`status_to=在库`。
- 两条共享同一 `event_group_id`,可一把捞出"新件替换了哪块旧件"。

### 6.3 高值/敏感件(尤其 GPU)防掉包

非数据介质返厂换新存在"以坏换好、实物截留"的流失口子。规则:

- **所有非数据介质换新一律 serial 级留痕**:旧件按固定资产编号核销、原厂新件带新 serial 入册,两条绑定同一 `event_group_id`。
- **GPU 等高值+涉出口管制件**:报废(含返厂换新的报废腿)走审批 + 要求返厂**影像证据**(`attachment_ref`)。
- 内存、光模块等低值件:serial 级留痕即可,不额外加审批,避免运维绕开系统。

### 6.4 定期盘点(账实核对)

盘点是整套防流失机制的**最后兜底**:前面的状态机/审批/履历防的是"有记录的流动",盘点防的是"没有记录的流动"(如实物被私自取走却无任何系统记录)。它是唯一能主动揪出"账实不符"的环节。

**本质:** 冻结一份系统应有清单(账)→ 派人物理核对实到(实)→ 把对不上的揪出、登记、按类型走各自处置。

**核心原则(务必守死):**

1. **快照原则**:发起盘点时冻结一份当时的系统账(`snapshot_at`),整个盘点过程以冻结的快照为比对基准,而非实时账;否则盘点期间配件仍在流动,基准漂移永远对不齐。
2. **盘点只发现问题,不修正账本**:盘点结果**绝不直接修改 `part` 状态**。查到差异只登记到 `stocktake_discrepancy`,怎么处置各自走原有流程(报废走报废审批、错位补校正履历…)。若允许盘点直接改状态,盘点本身就成了不留审批痕迹即可动配件的后门。
3. **盘盈盘亏禁止对冲**:盘盈与盘亏是两笔独立差异,系统**禁止**将其相互抵消归零。二者必须各自如实登记。(此条专门堵死"用盘盈冲盘亏 + 立即报废"洗白实物消失的经典流失手法。)

**四种盘点结果:**

| 结果 | 含义 | 处置 |
|---|---|---|
| 相符 | 账有、实有、位置对 | 通过,无需处置 |
| **盘亏** | 账有实无(最要命,直指流失) | **强制挂起追查**,禁止自动核销/报废/对冲;查清去向后再走对应流程 |
| **盘盈** | 账无实有(现场多出无档案配件) | 补录来源、补建档案(可能是私自替换/来源不明) |
| 错位 | 账实都在但位置/状态对不上 | 核实后**新增一条校正履历**(是新增说明性履历,不是改历史) |

**盘点方式:**
- 本单位现场件:**扫码逐件核对**——每件配件的固定资产编号做成条码/二维码,盘点员现场扫码,系统对快照实时比对标结果;无码/扫不出走手工录入。
- **在外借出/调拨件:走"函证核对"支线,不得因不在现场而跳过**。系统对相关外单位生成在借清单(固定资产编号 + 借出日 + 预期归还日),发出核实要求,对方反馈后录入 `stocktake_item`(实际状态 + `feedback_source` + 时间 + 经办人)。反馈"不见了"→照样进盘亏挂起流程。

**盘点频率(分层):**
- 打底:**每月抽查 + 年度全盘**(贴合现有制度)。
- 加密:**高值件(GPU)重点轮盘 + 借出在外件重点盯**。
- 以上共用同一套 `stocktake` 表,靠 `scope_kind` / `scope_value` 表达不同范围,不为不同盘点建不同结构。

> **盘亏处置链留待办**:盘亏被登记并强制挂起(状态锁死、不可被随手报废或对冲)后,往上如何上报(对接内部资产损失上报制度、走几级)**一期不定死**,留待摸清内部制度后补。一期先做扎实"揪出来并摁住"这一步。

## 7. 关键不变量(防流失核心,实现与测试都要覆盖)

1. `movement_log` append-only:任何路径都不得 UPDATE / DELETE 历史记录。
2. `part.current_status` / `current_loc_*` 仅为投影缓存,须始终能由履历最新记录重放得出;二者不一致视为数据故障。
3. 配件运行状态派生自所在服务器,系统内不存该值、不做级联刷值。
4. 服务器投运时,其上在用配件禁止拆下。
5. 服务器退役不级联报废配件,只生成逐件处置清单。
6. 报废一律审批(与配件所在位置无关)。
7. 目的地为外单位(`loc_to_kind=外单位`)的动作(借出/调拨)必须有已通过的审批单。
8. 借出必须有预期归还日;超期须能被查询/告警。
9. 换新的旧件报废与新件入库两条记录必须绑定同一 `event_group_id`。
10. 审批:三级逐级、一票否决、申请人回避且三级审批人互不相同。
11. 仅审批通过后才落配件状态变更履历。
12. 盘点以 `snapshot_at` 冻结的快照为比对基准,不用实时账。
13. 盘点结果不得直接修改 `part` 状态;差异仅登记,处置走原有流程。
14. 盘盈与盘亏禁止对冲归零,须各自如实登记;盘亏强制挂起,不可被自动核销/报废。
15. 在外借出/调拨件每次盘点必须被点到名(函证核对),不得因不在现场而跳过。
